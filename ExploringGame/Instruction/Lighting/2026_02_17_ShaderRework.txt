# GOAL
Update the rendering and shader to take into account the computed light levels of each room

# EXISTING IMPLEMENTATION
- Content\PointLightEffect.fx
	- shader with support for PointLights
- Rendering\PointLights.cs
	- managed a list of lights to be given to the shader
- Rendering\RenderEffect.cs
	- has two implementations of a shader, one using BasicEffect and one using the custom shader
- Rendering\ShapeBuffer.cs
	- contains the vertex buffers for a single call to the shader
- Services\ShapeBufferCreator.cs
	- responsible for deciding which ShapeBuffers to create from a WorldSegment

	- this is done by using the LightingGroup property of Room and taking all distinct values
2. In ShapeBufferCreator, we want one ShapeBuffer per LightingGroup and Texture Sheet
	- the shapes in this group are the Room itself, and Room that has it as its "LightingGroup", and all of their children

4. Change RoomLightData so the total light level is a property in memory, which can be updated by explicitly calling a "RecalculateLightLevel()" method

# SECOND PHASE TASKS (completed)
1. Create a "TwoPassRenderEffect" which first applies a BasicEffect and then applies the PointLightEffect (DONE)
	- until we start the third phase, the PointLightEffect will be commented out
2. Apply the lighting data from RoomLightingCalculator to the BasicEffect to get the ambient light for the room (DONE)
3. Determine the light level for dynamic objects and stamped shapes by determining what room they are in

## CONTEXT FOR SECOND PHASE
- ShapeBufferCreator (`Services\ShapeBufferCreator.cs`) is responsible for creating shape buffers for stamped shapes and active objects
- each dynamic object or stamped shape gets its own ShapeBuffer, meaning it gets its own rendering pass
- once within a ShapeBuffer, the rendering code makes no distinction between static or active shapes, as all it sees are triangles and vertices
- the interface IPlaceableObject currently describes any kind of dynamic object, however it does not have a Room property
	- we should actually expose a settable "Room" property, which fits logically in that interface as it defines "a shape that can be placed somewhere"
- "Stamped Shapes" may be created at runtime or at level build time
	- when added at runtime, the method `AddStampedShape` of LoadedLevelData is used to add a new entry to the list of shape buffers
	- these are the only kinds of shapes that can be added at runtime, anything else is loaded with the level
- any kind of IPlaceableObject should be lit according to the room its in
	- note that StampedShapes are immobile so they will never change rooms.
	- however, any other kind of object could be mobile and therefor we need a way to recompute what room they're in
- there is currently some code to detect what room an object is in, used by PathFinder. you may be able to reuse it.

## QUESTIONS AND ANSWERS FOR SECOND PHASE
Q. How frequently should we update the Room property for mobile objects?
	- unless we find that performance is a concern, we can try to update each frame
	- since its highly likely a shape is in the same room it was in, we can do a quick check to see if the shape is still in the same room 
		before we scan for what room its in now
Q. Is there a central movement/update system I should hook into, or should each object update its own room location?
	- this is something we need to research before we get to coding
Q. How does PathFinder determine what room an entity is in?
	- technically, it finds the closest Waypoint through basic distance comparison (see FindNearestWaypoint)
	- such an approach will actually work for lighting as well, since we have a graph of room lights
	- therefor, all we need to know is which room is closest to the entity
	- at this time we won't worry about edge cases and will naively assume that the closet room is the correct one
Q. When AddStampedShape<TStamp>(StampedShape<TStamp>) is called at runtime, should it automatically detect and assign the Room property?
	- that would be ideal since a stamped shape will never change rooms
Q. For dynamic objects, should I set ShapeBuffer.LightingGroup = dynamicObject.Room.LightingGroup when creating the buffer?
	- basically yes. We want to set the LightingGroup property based on the room the object is in
Q. If we're creating one ShapeBuffer per dynamic object, and each has potentially many triangles, do we need to worry about recreating vertex buffers frequently, or are these cached/reused?
	- triangles are never created at runtime. We calculate them when the level loads. Even StampedShapes, the only entities that can be added
	at runtime, will use precomputed triangles (we call those the "Shape Stamps")


# THIRD PHASE TASKS
GOAL: rework the PointLightEffect shader to work as a second-pass lighting effect, adding additional brightness around point lights

## CONTEXT FOR THIRD PHASE
- The shader definition is in `Content\PointLightEffect.fx`
- originally, this was meant to be the sole shader
- the lighting logic has two parts: one which only cared about the distance from each pixel to a light, and one that took into account the angle of the light relative to the normal
	- this two-part approach was needed because only using normal-based lighting resulted in some surfaces being completely dark
- the shader also had a "range" parameters which was an early attempt to prevent lights in one room from lighting up another

## PARTS WE DON'T NEED
- we don't need the "range" parameters anymore
- we don't need the distance-based lighting, since the ambient light will be handled by the BasicEffect and the point light effect will only be responsible for adding brightness around point lights

## DESIRED GOAL
- the shader should serve only to brighten and color pixels around light sources
	- we are not doing shadows
- the scene has already been rendered with the BasicEffect, so this shader should only modify pixels if it will make them brighter

## CHALLENGES
- originally we assumed a single list of PointLights would be used for the whole scene
	- however, now each lighted room is rendered with its own shader pass
	- therefor, we need a very efficient way of passing the PointLights for the current room to the shader
	- the lighting calculation does gather all light contributions, but I don't know if it remembers the actual light itself
